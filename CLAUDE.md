# CLAUDE.md - thunderbird-mcp

Fork of [TKasperczyk/thunderbird-mcp](https://github.com/TKasperczyk/thunderbird-mcp) — a Thunderbird extension + Node MCP bridge exposing full read/write mail, calendar, and contacts tools (pick up threads, reply, forward, delete, filters, calendar CRUD). Purpose here: an explicitly opt-in, separate write-capable companion to [[mailcorpus]] (`~/code/mailcorpus`), which stays deliberately read-only.

Origin: forked and security-reviewed 2026-07-02 (static review of upstream — clean code, no obfuscation, zero npm prod deps, no postinstall scripts) before adopting. See `~/code/mailcorpus/CLAUDE.md` roadmap entry for the review writeup.

## Guardrails (do not weaken without the user explicitly asking)

- **Review-required send is enforced at the Thunderbird preference level**, not just tool defaults: `extensions.thunderbird-mcp.blockSkipReview` is set `true` in the Thunderbird profile's `prefs.js` (also toggleable via the extension's Options page in Thunderbird). This makes `skipReview: true` on `composeMail`/`replyToMessage`/`forwardMessage` fail with an error instead of silently sending — every send/reply/forward opens a Thunderbird compose window for the user to review and click Send.
- **Confirm-before-delete is a Claude behavior rule, not a code-level gate** (this tool has no built-in delete confirmation). Before calling any delete/destructive tool (`deleteMessages`, `deleteFolder`, `emptyTrash`, `emptyJunk`, `deleteContact`, `deleteEvent`, `deleteFilter`), state exactly what will be deleted and wait for explicit user go-ahead in chat first.
- **Verify deletes independently — don't trust `deleteMessages`'s success response alone, especially right after account setup changes.** Root-caused 2026-07-02: on `vishal@illinois.edu`, deletes appeared to silently no-op (message still fully readable via `getMessages`, folder totals unchanged) despite `{"success":true}`. Actual cause: this account's Trash and Sent folders were **never subscribed** — it was originally set up narrowly for mailcorpus's read-only Inbox mirroring, so `Deleted Items`/`Sent Items` were excluded from the IMAP subscription list. `updateMessage(trash:true)` surfaced the real error (`"Trash folder not found"`); `deleteMessages` swallowed the equivalent condition and reported false success instead (a real thunderbird-mcp bug worth reporting upstream). Fix: in Thunderbird, right-click the account → **Subscribe...** → subscribe to `Deleted Items` and `Sent Items` (and `INBOX` — it turned out not to be subscribed either). Once subscribed, `listFolders` correctly reports `"type":"trash"` / `"type":"sent"` and queued deletes flush through (confirmed: a stuck 468-message bulk delete completed automatically the moment subscriptions were fixed, verified gone in both Thunderbird and Outlook). **Takeaway: after any account/profile change, re-run `listFolders` and check for `"type":"trash"` and `"type":"sent"` before trusting delete/send-related tools.**
- Extension listens on `127.0.0.1` only by default — do not enable the "listen on all interfaces" option.
- **`searchMessages` without `folderPath` searches ALL folders, including Deleted Items/Sent/Junk.** After a delete, a bare `from:X` count staying flat does NOT mean the delete failed — it likely just moved from INBOX to Trash, so the cross-folder total is unchanged. Always verify with `folderPath: ".../INBOX"` + `includeSubfolders: false` to check a specific folder's real content. This caused a false "over-deletion" alarm and later a false "delete isn't working" alarm on 2026-07-03 — both were verification bugs, not tool bugs.
- **Under heavy account load (e.g. a large one-time folder backfill), delete/move calls can return `{"success":true}` immediately but take real time to actually land server-side.** Confirmed 2026-07-03: `Sent Items` was backfilling from 0 to 69,570+ after the Trash/Sent subscription fix, and during that window several `deleteMessages` batches reported success with zero real effect for many minutes. Don't rush to retry or conclude failure — check `listFolders` for `Sent Items` count stability across a couple of calls first; if it's still climbing, wait longer before re-verifying.
- **`getMessages(rawSource:true)` fails for messages already in Deleted Items** (`NS_ERROR_FAILURE` / `getMsgInputStream`) — only works reliably on messages still present in their original folder (e.g. INBOX). Plan header/raw-source inspection (e.g. for `List-Unsubscribe`) *before* deleting, not after.

## Notes

- `scripts/bulk-delete-sender.mjs --from <substring> [--account <id>] [--folder <uri>] [--create-filter] [--yes]` — deterministic bulk-delete-by-sender: reads candidate message IDs from mailcorpus's SQLite index (fast, zero conversation tokens), fills any gap with a fully-paginated live `searchMessages` (also zero tokens — it talks to the bridge as a subprocess, not through the LLM), then calls `deleteMessages` in batches of 100. Dry-run by default; `--yes` required to actually delete. This is the standard tool for "delete all mail from sender X" requests — don't hand-roll per-message tool calls.
- `~/code/mailcorpus/scripts/scan_bulk_senders.py --min-count N --top M` — read-only heuristic scan of the mailcorpus index that ranks senders by bulk/promotional signals (no-reply-style addresses, promo keywords, unsubscribe-link presence, low subject variety) for human review before any delete. Flags false positives itself (real people whose correspondence just repeats subjects) — always sanity-check the list before acting, don't blindly delete everything scored >0.
- Extracting `List-Unsubscribe`-style footer links from mailcorpus's stored `body_text` (regex for a URL near the word "unsubscribe") is a cheap, zero-token way to surface real unsubscribe links after mail is already deleted from the live account — mailcorpus keeps historical bodies regardless of live-mailbox state. Links from university mail are typically wrapped by a Proofpoint `urldefense.com/v3/__...` redirector — safe to click as-is, it forwards to the real target.

- **`searchMessages` return shape varies:** a plain **array** normally, but the `{messages, totalMatches, offset, limit, hasMore}` envelope only when `offset` is passed. Script code reading `result.messages` without passing `offset` silently sees 0 hits (bit a canvas-mcp session 2026-07-21 against a 143k-message inbox). Handle both: `Array.isArray(r) ? r : r.messages`.
- **If the `thunderbird` MCP server shows "Connected · tools fetch failed"** (Thunderbird wasn't running when the Claude Code session started), the session can't recover the MCP tools — launch Thunderbird (`open -a Thunderbird`) and drive `mcp-bridge.cjs` as a subprocess instead (same JSON-RPC pattern as `bulk-delete-sender.mjs`; worked example: threaded `replyToMessage` via `searchMessages` → find target Message-ID → reply, review window still enforced).
